# 2026.287.1418 — chore: adopt sdk v0.2026287.1411 — a download destination now expands a candy's own vars

## Summary

Adopts `github.com/opencharly/sdk v0.2026287.1411`, which fixes a download **destination** not expanding a candy's own `var:` on a `target: local` deploy.

This plugin hands its executor straight to `kit.WalkPlans`, so it is the component that renders those steps for host deploys — which is why the fix only reaches authoring once this module's pin moves.

**The defect it adopts** (`opencharly/sdk#381`, fixed in `#382`): `kit.RenderDownloadScript` quoted the two author strings **differently** — the URL through `ShDoubleQuote` (so `${FC_VERSION}` expanded, which is why the download itself succeeded) and `to:` / `extract_include` through `ShQuoteArg`, which single-quotes anything containing `$`. Measured on a real `target: local` deploy:

```
0  7.11M  … 100  7.11M                    ← curl received the whole tarball
tar (child): /var/cache/charly/firecracker/firecracker-v1.17.0-x86_64.tgz: Cannot open: No such file or directory
$ find / -maxdepth 4 -name '*FC_TARBALL*'
/home/arch/${FC_TARBALL}                  ← a FILE named after the unexpanded string
```

**Files:** `candy/plugin-deploy-local/go.mod` + `go.sum` (both pins), and `host_render_test.go` (the adoption gate).

**BOTH pins move together** — `sdk` → `v0.2026287.1411` and `spec` → the version that sdk requires. Adopting one alone leaves the other's symbols unresolved, and that is measured here rather than assumed: downgrading only the `sdk` for the control below produced a **build** failure, because the pre-fix sdk cannot compile against the new spec.

## How tested

**The new gate** pins the adopted behaviour **from this plugin's entry point** — the same shape as the existing `sdk#302` guard already in that file:

```
$ go test ./... -run HostDownload -v
  --- PASS: TestWalkPlans_HostDownloadGuardsAndEmptyTo
  --- PASS: TestWalkPlans_HostDownloadExpandsCandyVarInDestination
```

It walks a `download:` step whose destination names the candy's own var and asserts the emitted script (a) carries the **expanded** path, (b) creates the substituted directory, and (c) still parses under `sh -n`. If anyone downgrades this module below the fix, that test is what fails.

**The control** — both pins returned to their pre-fix pair:

```
$ go get github.com/opencharly/sdk@v0.2026273.207 github.com/opencharly/spec@v0.2026273.203
--- FAIL: TestWalkPlans_HostDownloadExpandsCandyVarInDestination
      the destination kept its unexpanded var, so the shell writes a file literally named that:
```

**Module gates** on the committed tree:

```
$ gofmt -l .            → clean
$ go build ./...        → ok
$ go vet ./...          → ok
$ go test -count=1 ./...→ rc=0
$ charly box validate   → OK — checked 1 candy, 7 distros, 7 builders; 0 warnings, 0 errors
```

**The live proof this repo's own AGENTS.md names** — *"the changed path is exercised by any `target: local` deploy"* — is a concrete deploy that is currently failing for exactly this reason: `opencharly/layer-firecracker`'s `check-firecracker-posture` bed, a disposable VM with a nested `local:` member whose candy downloads the pinned VMM tarball to a `${VAR}` destination. It can only run against `main`, so it is **run immediately after this merge and its result posted on this PR**; before this adoption it fails with the `Cannot open: No such file or directory` message above, which is the defect being fixed.

The fix's own live proof — the rendered script executed in a real guest, materialising the artefact at the **pinned** sha256 `298055d97266f3dc…` where it previously failed — is in `opencharly/sdk#382`.
